# Discovery refresh and latency work

## What runs

`python3 -m scripts.egress_refresh --interval 300 --duration 21600` starts an immediate metadata refresh, then polls every five minutes until six hours have elapsed. VPN Gate and VPN Jantit are fetched concurrently, once per cycle, with no automatic authentication retries. The output is atomically replaced, includes per-source status, expires after 15 minutes, and never authorizes a route. If the process is killed before publishing, the previous snapshot still expires; partial failures do not retain the failing source's old rows. A filesystem lock prevents two local writers for the same path. If a refresh takes longer than its cadence, there is no catch-up burst. Stop with Ctrl-C or SIGTERM; an in-flight request can take up to its 60-second deadline to stop.

`deploy/nyx-catalog-refresh.service` is an example **user-managed** systemd unit. Edit `WorkingDirectory` to the actual checkout, install it under `~/.config/systemd/user/`, run `systemctl --user daemon-reload` and `systemctl --user enable --now nyx-catalog-refresh.service`. The unit restarts the metadata worker when its six-hour bounded run ends, including after failure. This requires a machine that stays online and has provider access; user services generally stop when the user session ends unless the machine is configured to keep them running. It neither restarts a VPN tunnel nor modifies an active session. This service has not been installed or deployed here, and the local JSON is not yet exposed to the Android catalog URL. Polling is near-real-time at best, not instantaneous provider events.

The GitHub discovery workflow has a six-hour **bounded diagnostic** schedule at minute 17, plus push/manual triggers. GitHub schedules run only from the default branch; this checkout is a non-default session branch, so its schedule is **not active**. Even on the default branch a scheduled run can be delayed or dropped; it exercises two short refresh cycles, not six-hour VPN hosting, feed distribution, or a tunnel restart. Do not use Actions runners as an always-on VPN service: [GitHub Actions terms](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features) restrict application hosting. No change was made to main. See [GitHub's schedule limitations](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

## Latency

The issued-route geography checks now make their four HTTPS requests in parallel through the authenticated SOCKS/TLS route instead of sequentially. All successful independent observations still participate in the exact-IP country/conflict checks, and the explicit measured-IP lookup, UDP test and tunnel-drop safeguards are unchanged. The report separates individual runner-origin cold HTTPS request times from the wall time of the concurrent phase. This can shorten verification/startup, not necessarily the underlying VPN packet latency; it does not prove phone/Tehran ping or choose a faster runner location. GitHub-hosted runner region is not pinned here. No active lease is automatically moved when a new discovery snapshot appears.

The [German issued-route diagnostic](https://github.com/asomethinggood-sys/My-small-project/actions/runs/42857842028) selected zero eligible candidates in its VPN Gate snapshot, so no authenticated route or live optimized latency measurement was obtained. It failed closed and did not issue phone credentials. The parallel collection is covered by a synchronized unit test but still needs an actual issued-path comparison.

Live 30-country/1,000-server capacity, legal provider provisioning and sharing, permanent hosting and publishing, production session routing, real end-to-end phone latency optimization and stable release signing remain outstanding. See `nyx-multi-provider-discovery.md` and `nyx-country-route-followup.md`.
