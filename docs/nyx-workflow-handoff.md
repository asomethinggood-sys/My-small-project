# Bounded workflow handoff test

One GitHub Actions run **can** dispatch another before the first completes. The previous discussion of branch-only cron schedules did not rule this out. GitHub documents `workflow_dispatch` as an exception to the normal suppression of events generated by `GITHUB_TOKEN`; the target workflow must exist on the default branch, but a dispatch can target another ref. Here `.github/workflows/vpn.yml` exists on main, so a branch-scoped test was possible without changing main.

The [parent diagnostic 42859997189](https://github.com/asomethinggood-sys/My-small-project/actions/runs/42859997189) used its job-scoped Actions write token to dispatch [successor 42860013469](https://github.com/asomethinggood-sys/My-small-project/actions/runs/42860013469) to the session branch. The parent observed the exact successor, with the same commit, running before the parent finished. Both completed successfully. The successor did not dispatch another run, start a VPN, touch shared releases or alter main. The test used no user-provided credential and did not retry denied operations.

The handoff was subsequently integrated into the provider discovery workflow: [parent run 42860661102](https://github.com/asomethinggood-sys/My-small-project/actions/runs/42860661102) started [successor 42860681981](https://github.com/asomethinggood-sys/My-small-project/actions/runs/42860681981) before completing; the successor fetched both providers and uploaded a sanitized catalog artifact. The parent then completed two more bounded refresh cycles. Both runs succeeded. The dispatch is guarded by an explicit push marker, runs once, and the successor does not dispatch again.

This proves dispatch and an actual metadata refresh, not a live six-hour restart or seamless VPN. GitHub can queue or fail a successor; a new runner has a different process/network state and cannot inherit active connections. Safe handoff of any real service would need a stable reachable control plane, health/readiness checks, bounded lease lifetimes, authorization, secure credential handling, and a plan for existing connections; the existing personal trial deliberately does not rotate an issued session. GitHub's [Actions terms](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features) restrict use of hosted runners as application/service infrastructure. The workflow here intentionally dispatches at most one short test and cannot recursively chain. The old default-branch VPN loop is separate, exposes credentials, and was not modified or started by this test.

Periodic metadata refresh remains available as an operator-managed service described in `nyx-refresh-latency.md`; no such service or live Android feed has been deployed. The branch-only six-hour cron remains inactive unless the workflow exists on the default branch.
